## Ограничения

- Тестовый runtime, стабильность и реальное покрытие нельзя измерить без исполняемого набора.
- Нельзя оценить качество assertions, fixtures и поддерживаемость на выборке: тестового кода нет.
- Зависимости не устанавливались, поскольку пригодной тестовой команды не обнаружено; вывод о сценариях и фреймворках основан на манифестах и прямой инвентаризации.
- Отсутствие проектного Guard-контекста проверено и нейтрально; оно не уменьшает уверенность в выводе.
- Предыдущий сопоставимый аудит качества тестов недоступен; этот результат становится базовой точкой для следующего сравнения.

Уверенность в основном выводе высокая: полная история Git доступна, а отсутствие тестовых файлов, фреймворков, сценариев, CI и настроек покрытия подтверждено на уровне всего репозитория.

## Шаги по улучшению

1. **Создать backend integration suite.** Почему важно: auth, chat, message, topic и Socket.io — критичные границы продукта без регрессионной защиты. Первый шаг: настроить test database и один сценарий register/login → create DM → send message с проверкой БД и события. Готово, когда сценарий стабильно проходит локально.
2. **Добавить браузерный happy path с двумя пользователями.** Почему важно: только e2e докажет видимую доставку сообщения через frontend, API и realtime. Первый шаг: настроить Playwright для входа, открытия чата, отправки и получения сообщения. Готово, когда сценарий проходит без ручных действий.
3. **Подключить тесты к CI.** Почему важно: локальные тесты не остановят регрессию при слиянии сами по себе. Первый шаг: создать workflow для install и backend integration suite. Готово, когда ошибочный тест блокирует pull request в `main`.
4. **Разделить unit, integration и e2e уровни.** Почему важно: смешение MongoDB, sockets и browser effects сделает один общий набор медленным и хрупким. Первый шаг: добавить scripts `test:unit`, `test:integration`, `test:e2e`, общие factories и cleanup. Готово, когда каждый уровень запускается отдельно и имеет явные зависимости.
5. **Документировать запуск и убрать падающую заглушку.** Почему важно: сейчас разработчик получает ложную команду вместо способа проверки. Первый шаг: заменить script в `websocket-example` реальным smoke test или удалить его и добавить раздел `Testing` с env/test database setup. Готово, когда инструкции воспроизводятся с чистого checkout.
