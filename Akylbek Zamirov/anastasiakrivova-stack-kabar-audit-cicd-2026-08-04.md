# Аудит CI/CD репозитория anastasiakrivova-stack/kabar

## Краткое резюме

- Основная ветка и путь доставки практически не защищены: CI/CD-пайплайна — автоматического пути, который проверяет изменения, — нет, обязательные проверки не блокируют слияние, а связь опубликованной версии с проверенным кодом не видна. Итог: **4 из 100**, уровень `bad`.
- Это не полное отсутствие инженерной основы: `backend` и `client` умеют собираться локально, для `client` доступен lint, а у каждого npm-пакета есть lockfile. Эти команды подходят для первого CI.
- Уверенность средняя: отсутствие workflow, запусков, rulesets и статусов подтверждено, но отдельные настройки защиты ветки и Render недоступны для полной проверки.
- Самый полезный следующий шаг — унифицировать локальные команды и добавить минимальный GitHub Actions CI для pull request и `main`; после стабильных зелёных запусков сделать его обязательным.

## Что было проверено

- Конфигурации распространённых CI/CD-систем, включая `.github/workflows/`, `.gitlab-ci.yml`, `Jenkinsfile`, `.circleci/` и другие стандартные пути.
- Скрипты и lockfile в `backend/package.json`, `client/package.json`, `websocket-example/package.json`.
- Наличие workflow, запусков, check-runs, статусов коммитов, rulesets, environments, releases и deployments на GitHub.
- Автоматизация сборки, артефактов — результатов сборки, например пакета или образа, — контейнеров, релиза, деплоя, продвижения между окружениями и отката.
- Проектный Guard-контекст отсутствует; дополнительных правил владельца, меняющих охват или оценку, нет.

## Результаты

### Главный ответ
> [!CAUTION]
> **Вопрос аудита:** Насколько текущий процесс CI/CD защищает основную ветку и путь доставки от непроверенных изменений и какая последовательность следующих шагов сделает его надёжным?
>
> **Ответ:** Защита сейчас крайне слабая, с уверенностью `medium`: CI/CD-пайплайна, реальных автоматических проверок и блокирующего gate — проверки, способной остановить плохое изменение, — нет. Надёжность следует наращивать по порядку: единые команды, валидный CI, реальные проверки, обязательный gate, недостающие категории проверок, стабилизация, затем артефакты, деплой, релиз и откат.

### Расчёт оценки

Оценку повысили локальные build/lint-команды и lockfile; сильнее всего снизили полное отсутствие CI, gate и управляемой доставки. Компактный расчёт: **12 из 50 баллов критериев = 24/100; минус 20 за критический риск отсутствия CI; ограничение 39 не меняет результат; итог 4/100**.

### Ключевые находки

| Находка | Влияние | Уверенность | Доказательство | Следующее действие |
| --- | --- | --- | --- | --- |
| Активное приложение не имеет CI/CD-пайплайна | Изменения могут попасть в `main` без build, lint, typecheck или tests. | Высокая | Workflow=0, runs=0, check-runs=0; конфигурации CI/CD отсутствуют. | Создать минимальный GitHub Actions workflow после унификации команд. |
| Проверки не блокируют слияние | Даже будущий advisory CI не защитит ветку, пока не станет обязательным. | Средняя | `main protected=false`, rulesets=0, checks отсутствуют. | После стабильного CI включить обязательные checks или ruleset. |
| Деплой и релизы не прослеживаются из репозитория | Нельзя подтвердить, какой commit опубликован, что проверено и как откатиться. | Средняя | Render demo указан, но releases, environments, deployments и rollback-путь отсутствуют. | После блокирующего CI связать доставку с commit/tag и описать rollback. |

## Доказательства

- В репозитории отсутствуют `.github/workflows/` и конфигурации других распространённых CI/CD-провайдеров.
- GitHub показывает ноль workflow, запусков, rulesets, environments, releases, deployments и check-runs для аудированного коммита.
- `backend/package.json` и `client/package.json` содержат `npm run build`; `client/package.json` содержит `npm run lint`.
- `backend/package-lock.json`, `client/package-lock.json` и `websocket-example/package-lock.json` дают основу для воспроизводимой установки через `npm ci`.
- Тестовые файлы и полноценные test-скрипты не обнаружены; шаблонная падающая команда в `websocket-example` не считается реальной проверкой.
- README указывает живую демонстрацию на `https://kabar.onrender.com`, но её автоматическая связь с репозиторием не подтверждена.

## Ограничения

- Endpoint подробной защиты ветки недоступен для чтения; вывод о неблокирующем состоянии основан на `protected=false`, пустых rulesets и отсутствии checks.
- Настройка Render может существовать вне репозитория и GitHub metadata, поэтому способ фактического деплоя не подтверждён.
- Checkout содержит только один коммит; полная история тегов локально не видна, хотя GitHub Releases возвращает пустой список.
- Контейнеризация отсутствует и отмечена как неприменимая, без штрафа. Скорость feedback не оценивалась до появления базового пайплайна.
- Guard-контекст проекта отсутствует, поэтому его влияние на охват и оценку нейтрально.
- Предыдущий завершённый аудит CI/CD для сопоставления недоступен; текущий результат становится базовой точкой для следующего сравнения.
